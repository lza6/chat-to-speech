1. 上下文与直觉

为什么做这个

项目是纯前端单文件静态页（demo.html + sw.js + site.webmanifest），三闭环：AI 对话 / 文本转语音 / 整页朗读。v3 已上线生产（git tag v3.0.0），但有三个被忽略的"屎山"：

  1. 推理清洗太弱：v3 的 cleanAssistantText 只匹配 3 个固定前缀（Here's a thinking process / 思考过程 / 分析用户输入），推理模型一旦换前缀格式（XML <think> 标签、markdown ### Reasoning 标题、思考: 行内前缀）就漏过滤，整页朗读把思考过程读出来。
  2. 合成是串行瓶颈：v3 的 prefetch 只预取下一块（最多 2 块在途），长文本 10 段要等 单块×10。官方限流 3 req/s，并发 3 本可把耗时压到 单块×3，但没人做。
  3. 文档数字三处打架：代码 e2e-test.cjs 17 项 / workflow_status.md N4 表 16/16（v2 残留旧枚举）/ README.md 13/13（更早陈旧），三套数字完全不对应，且 N4 表的 T1="主色靛蓝/紫渲染" 与代码 T1="页面加载 HTTP 200" 整套错位。上线生产却没人复跑 E2E 拿真实通过数。

直觉判断：这三个都不是"加新功能"，而是还债。推理清洗的脆弱会在模型换前缀时静默漏读，串行瓶颈在长文本场景肉眼可见，文档打架会让下一个接手的人（或 AI）误判基线状态。优先级：清洗 > 文档 > 并发（清洗影响正确性，文档影响协作，并发影响体验）。

关键修正：规则 4 原始正则 [:：]?\s*[\s\S]*? 会误删正文"思考是人类..."（因 [:：]? 可选致匹配整段）。改为 [:：]?\s*\n[\s\S]*?（要求前缀后必须有换行），正文场景由规则 5 兜底。

2.2 P1-3 并发合成池（demo.html:554-580 + 595-634）

手写 pLimit(3) 并发池（无依赖库），把 v3 串行 prefetch（最多 2 在途）改为 3 并发预取 + 播放时预取下一批，并带 429 退避降并发：

function pLimit(max) {
  let active = 0, queue = [], currentMax = max;
  const next = () => {
    if (active >= currentMax || !queue.length) return;
    const item = queue.shift(); active++;
    Promise.resolve().then(item.fn).then(
      v => { active--; item.resolve(v); next(); },
      e => { active--; item.reject(e); next(); });
  };
  return Object.assign(
    fn => new Promise((res, rej) => { queue.push({fn,resolve:res,reject:rej}); next(); }),
    { lowerMax: to => currentMax = Math.max(1, to),  // 429 退避
      restoreMax: () => currentMax = max });
}
// synthChain 内：维持 3 在途，播放第 i 块时预取第 i+3 块
if (i + 3 < chunks.length) prefetch(i + 3);

设计要点：

  • 按序播放不变：prefetchPromises[i] 数组缓存 promise，播放循环 await prefetchPromises[i]（幂等，resolved 再 await 立即返回），顺序由索引保证。
  • 维持 3 在途：初始预取 0/1/2，播放第 i 块时预取第 i+3 块，始终有 3 个在途。
  • 429 退避：fetchTTSChunk reject 且消息匹配 /429|rate.?limit/i → ttsLimiter.lowerMax(2) 降并发，状态栏提示。
  • 幂等 prefetch：prefetchPromises[i] 已存在则直接返回，避免重复排队。

Q1. v3 原始 cleanAssistantText 匹配几个前缀？v4 升级为几规则管线？
✅ B。v3 匹配 3 前缀（Here's a thinking process / 思考过程 / 分析用户输入），v4 升级为 7 规则结构化管线（XML 标签 / md 代码块 / md 标题区块 / 多前缀块 / 行内前缀 / 尾部剥离×2）。
Q2. 规则 4（thinking-prefix-block）为什么要加 \n 要求？不加会怎样？
✅ B。原正则 [:：]?\s*[\s\S]*? 因 [:：]? 可选，对 思考是人类特有的能力。这是正文。（无换行）会匹配整段并删除。加 \n 要求前缀独占一行，正文场景由规则 5（行内前缀，要求冒号）兜底。
Q3. pLimit 并发池收到 429 时做什么？为什么 max 设 3？
✅ B。官方限流每 IP 每端点 3 req/s，max=3 恰卡边界。收到 429 调 lowerMax(2) 降并发让排队任务慢下来，配合 fetchTTSChunk 的指数退避重试。当前未自动 restoreMax，待 v4 Phase 2.3 补定时恢复。
Q4. 并发池如何保证"按序播放"不被并发破坏？
✅ B。prefetchPromises[i] 幂等（已存在则直接返回），播放循环 await prefetchPromises[i] 等第 i 块就绪才播。即使第 5 块先于第 2 块完成，播放仍从 i=0 顺序 await，不会跳序。
