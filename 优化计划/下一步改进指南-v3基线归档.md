## 〇、第一性原理：这个工具的本质是什么？

剥到最底层，"在线聊天转语音"做的是三件事的串联：

```
[意图表达] → [语义生成/文本提取] → [文本→声波] → [人耳]
   输入框         聊天模型/整页提取      TTS 引擎链       播放
```

任何一环断裂，工具就失效。v3 已在"文本→声波"环做了三级降级链（在线→浏览器→文本），但仍存在三类**根本性脆弱**：

1. **外部依赖不可控**：TTS 端点 `speech.ai.unturf.com` 持续 502、聊天端点模型名漂移、库 `uncloseai.js` 是黑盒。工具的可用性被别人决定。
2. **降级路径质量塌方**：在线引擎质量高但不可控；降级到浏览器 SpeechSynthesis 时音色机械、Linux 无中文包；再降级到文本兜底已无声。降级链是"保活"而非"保好"。
3. **单文件架构的天花板**：1188 行 HTML 已接近单文件可维护极限，无构建无模块化，难以引入现代前端能力（组件化、类型、WASM、WebGL 可视化）。

v4+ 的核心命题：**把"保活"升级为"保好"，把"被外部决定"升级为"用户自给自足"**，同时不破坏 v3 的"纯前端、无构建、单文件可部署"的核心价值。

1. **RED 先行**：每个测试 ID 先写断言跑一次，确认 FAIL（功能未实现）。

3. **REFACTOR**：在测试保护下重构，跑一次确认仍 PASS。

## 二、v4 迭代路线图（韧性 + 自主）

**v4 主题词：让工具不再被别人决定。**

### P0-1（v4）引入引擎1.5：本地 WASM TTS，摆脱外部端点 + 系统音色双重依赖

**根因**：v3 的降级链在"在线端点宕机"且"系统无中文语音包"时直接塌方到文本兜底（无声）。这是最严重的体验断裂。

**方案**：在引擎1（在线）和引擎2（浏览器 SpeechSynthesis）之间插入引擎1.5 —— 基于 WASM 的本地高质量 TTS，不依赖外部服务，不依赖系统语音包。

**候选技术（按优先级）**：

> ⚠️ 以下候选信息为知识库推断 + 官方自托管仓库背书，**未联网验证**（WebSearch/WebFetch 权限被拒）。落地前必须执行「第九·三节 验证前置任务」。下表所有数字/许可/可用性均标 `待验证`。

| 候选 | 模型 | 大小（待验证） | 质量 | 中文 | 许可（待验证） | 落地难度 |
|------|------|------|------|------|------|---------|
| **piper**（首选） | VITS | ~40-200MB/语音 | 高（待实测） | ✅ 多说话人（待确认中文模型名） | MIT（待验证） | 低（据称 WASM 官方支持，待验证）|
| **Kokoro**（新增候选） | 82M 参数、34 声道、24kHz | 更轻量（待确认确切体积） | 高（待实测） | ✅ 多语种含中文（待确认） | Apache-2.0 | 低-中（**官方自托管已内置，适配树莓派/边缘；WASM 构建是否存在待联网确认**）|
| sherpa-onnx | VITS/Matcha | ~30-150MB | 高 | ✅ | Apache-2.0（待验证） | 中 |
| vosk-wasm | Kaldi | ~50MB | 中 | ✅ | Apache-2.0（待验证） | 中 |
| Coqui TTS JS | XTTS | 大（待验证） | 极高 | ✅ | MPL（待验证） | 高 |

> **候选背书来源（分析报告新洞察）**：官方 `uncloseai-speech` 自托管仓库（`git.unturf.com/engineering/unturf/uncloseai-speech.git`）已内置 **Piper TTS**（"100+ 英语语音、纯 CPU、ONNX、最快引擎"）与 **Kokoro TTS**（8200 万参数、34 声道、24kHz、Apache-2.0）。F5-TTS 模型约 1.5GB。**若 piper WASM 不可用，Kokoro 82M 参数比 piper 更轻量，是更优的 WASM 候选**——落地时优先确认 Kokoro 是否有 WASM 构建（补入 V1-V5 验证清单）。

> **禁止落地时直接套用上表数字**。落地第 1 步必须联网查 piper 官方模型库（`https://github.com/rhasspy/piper`），确认：(a) 中文模型是否真实存在及其确切文件名；(b) 模型体积；(c) WASM 运行时是否已发布到 npm/CDN。若 piper 无可用中文 WASM，**先查 Kokoro 是否有 WASM 构建（82M 参数更轻量）**，再退 sherpa-onnx。

**落地技术点**：
1. 动态 `import()` piper-wasm 包，按需加载模型（首次使用时下载，IndexedDB 缓存）。
2. 模型选择器：默认中文女声（**落地时从 piper 官方模型列表选取中文模型，禁止预设未验证的模型名**），可切换男声。
3. 降级链调整：`引擎1（在线）→ 引擎1.5（WASM）→ 引擎2（浏览器）→ 引擎3（文本）`。
4. WASM TTS 可产出 PCM/WAV blob，**离线模式也能下载**（修复 B4）。
5. 徽章三态：`● 在线高质量 / ● 本地高质量 / ● 浏览器机械 / ● 离线文本`。

**验收标准**：
- 断网 + 无系统中文包环境下，输入中文文本能产出可听的高质量语音（非机械音）。

- piper-wasm npm 包是否存在、是否维护活跃，待联网确认。

**依赖**：piper-wasm npm 包 / CDN。

### P0-2（v4）推理清洗结构化：从前缀白名单升级为标签剥离

**根因**：v3 的 `cleanAssistantText`（`demo.html:881`）用**单条正则匹配 3 个固定前缀白名单**（`Here's a thinking process` / `思考过程` / `分析用户输入`），到首个空行整块剥离。问题不在前缀数量，而在**固定白名单无法覆盖模型输出格式变化**——XML 推理标签、markdown 区块（`### 思考过程`）、新前缀（`思考:`）均不在白名单内，模型一换输出格式即失效。

**方案**：多层结构化清洗管线。

```
输入文本
  ↓
1. XML 标签剥离：推理标签整段（开标签到闭标签）
  ↓
2. Markdown 区块剥离：```thinking ... ```、### 思考过程 / ### Reasoning 整段到下个标题
  ↓
3. 前缀整块剥离：扩展现有正则为多语种多前缀白名单
  ↓
4. 尾部剥离：模型有时在答案后追加"以上是思考过程"等
  ↓
5. 空结果回退：全被剥光则返回空（上层跳过朗读）
```

**落地技术点**：
1. 清洗规则数组化，每条带 `name / pattern / strategy(strip|replace)`。
2. 支持"测试夹具"：维护 `test-cases/推理清洗样本.json`，含 20+ 真实推理回复样本，E2E 校验清洗后等于期望正文。
3. 清洗规则可配置（用户可加自定义前缀白名单）。

**验收标准**：
- 20 样本清洗后 100% 等于期望正文（E2E 新增 T_CLEAN_1）。
- 空正文返回空标记，上层跳过朗读（E2E 新增 T_CLEAN_2）。

**风险**：过度清洗可能误删正文。需夹具回归保护。

### P1-1（v4）Service Worker 跨域 CDN 缓存：离线时聊天功能不全挂

**根因**：v3 的 `sw.js`（第 32 行注释）明确"跨域资源不缓存"，`fetch` 事件中 `url.origin !== self.location.origin` 直接 return，导致离线刷新页面虽不白屏（demo.html 已缓存），但 `uncloseai.js` 加载失败 → 闭环①（聊天）全挂。

**方案**：对 `uncloseai.com`、`cdn.jsdelivr.net`、`cdnjs.cloudflare.com` 三个跨域源启用"stale-while-revalidate"缓存策略。
- 跨域响应是 `opaque` 类型（status 0），不能读取但**可以缓存和回放**。
- 策略：网络优先 → 失败回放缓存 → 缓存过期后台异步更新。

**落地技术点**：
1. sw.js 增加跨域资源白名单 `CROSS_ORIGIN_CACHEABLE`。
2. 跨域 fetch 用 `cache.add(req)`（不读 body，只存）。
3. 离线时 `caches.match` 回放 opaque 响应有效。
4. 缓存版本号升级触发清理。

**验收标准**：
- 首次在线访问后，断网刷新页面，`uncloseai.js` 从缓存加载，聊天 UI 渲染成功（E2E T_SW_1）。
- 离线时聊天发送会失败（端点不可达），但 UI 不白屏，提示"离线模式，聊天不可用"（E2E T_SW_2）。

**风险**：跨域缓存策略复杂，opaque 响应无法校验时效，可能缓存过期版本。需设最大缓存年龄（如 7 天）。

### P1-2（v4）朗读字级高亮：karaoke 式跟随

**根因**：v3 朗读时无视觉反馈，用户不知道读到哪了。长文本体验差。

**方案**：
- 在线引擎1：分块播放时，对应文本块高亮（已知 chunk 边界）。
- 浏览器引擎2：`SpeechSynthesisUtterance.onboundary` 事件提供 charIndex，可做字级高亮。
- WASM 引擎1.5：若支持时间戳对齐则字级，否则块级。

**落地技术点**：
1. 输入框改为 `contenteditable` 或只读镜像层，高亮用 `<mark>` 包裹当前块/字。
2. 自动滚动当前块到可视区（`scrollIntoView({behavior:'smooth', block:'center'})`）。
3. 高亮颜色用 `--accent` 半透明。
4. 停止时清除所有高亮。

**验收标准**：
- 朗读时当前块高亮 + 自动滚动（E2E T_HL_1）。
- 停止后高亮清除（E2E T_HL_2）。
- 浏览器引擎下字级高亮（如支持 boundary 事件）（E2E T_HL_3）。

**风险**：`onboundary` 在部分浏览器不触发或 charIndex 不准。需块级兜底。

### P1-3（v4）并发合成：在线分块并发 fetch + 顺序播放

**根因**：v3 的 `prefetch` 只预取下一块（`prefetch(i+1)`），长文本合成慢。N 块文本串行 fetch 是 N 倍延迟。

**方案**：并发 fetch 所有块（限制并发 3，与官方限流上限对齐），按序播放。
```
fetch chunk[0..N] 并发（Promise.all 分批）
→ 播放 chunk[0] 时 chunk[1..3] 已就绪
→ 播放 chunk[i] 时若 chunk[i+1] 未就绪则等待
```

**落地技术点**：
1. 并发池 `pLimit(3)` 模式（无依赖库，手写 Promise 池）。
2. 播放逻辑不变，只是 blobCache 命中率提高。
3. **官方限流硬约束（分析报告新洞察）**：上游官方文档明确"每 IP 每端点每秒 3 个请求"——并发 max=3 恰好卡在边界，>3 必触发 429。**必须实现 429 退避降并发**：收到 429 立即降 max=2 并指数退避重试（`fetchTTSChunk` 已具备指数退避基座），恢复稳定后再回 max=3。

**验收标准**：
- 10 块文本合成总耗时接近单块耗时 × 3（而非 × 10）（E2E 计时 T_PERF_1）。
- 并发不破坏顺序播放（E2E T_PERF_2 顺序断言）。
- 触发 429 后自动降并发且不中断播放（E2E T_PERF_3，用 mock 端点返回 429 验证）。

**风险**：端点限流 429 会打断顺序播放。退避降并发 + 播放侧等待补位（P1-3 配套）。

## 四、v6+ 迭代路线图（生态 + 平台化）

**v6+ 主题词：从工具到平台。**

### v6 候选方向

| 方向 | 描述 | 价值 | 难度 |
|------|------|------|------|
| **朗读书签云端同步** | IndexedDB + 远端同步（用户自建后端）| 多设备续读 | 中 |
