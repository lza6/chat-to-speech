## 〇、第一性原理：这个工具的本质是什么？

剥到最底层，"在线聊天转语音"做的是四件事的串联：

```
[意图表达] → [语义生成/文本提取] → [文本→声波] → [人耳感知]
   输入框         聊天模型/整页提取      TTS 引擎链       播放 + 视觉反馈
   语音听写        推理清洗             在线/WASM/浏览器   频谱/高亮/续读
```

**任何一环断裂，工具就失效。** 但"失效"有程度之分：

| 失效等级 | 表现 | 用户感受 | v4.1 现状 |
|---------|------|---------|---------|
| L0 完全哑火 | 无声、无反馈、白屏 | 工具死亡 | ✅ 已消除（三级降级链 + SW 离线缓存）|
| L1 降级塌方 | 有声但机械/无中文/不可下载 | 能用但难用 | ⚠️ 仍存在（Linux 无 zh 包时 → 文本兜底；WASM 引擎1.5 未落地）|
| L2 体验断裂 | 有声但无字级高亮/无续读/无可视化 | 能用但低端 | ⚠️ 普遍存在（P1-2/P2-* 未落地）|
| L3 被外部决定 | 端点宕机/模型漂移/库黑盒 | 可用性被别人决定 | ✅ 已缓解（P0-3 配置中心让用户自带端点 + 引擎开关）|
| L4 单文件天花板 | 1470 行难维护/无类型/无组件 | 演进受阻 | ⚠️ 接近极限（v6 考虑模块化）|

**v4.2+ 的核心命题**：

> **把"保活"彻底升级为"保好"（WASM 引擎1.5 落地 + 字级高亮 + 视觉反馈），把"被外部决定"彻底升级为"用户自给自足"（配置中心已落地，补真机 WASM 自托管），把"单文件能用"升级为"单文件可演进"（v6 模块化但不破坏部署承诺）。**

同时不破坏 v4.1 已固化的的核心价值三角：

1. **纯前端**（无后端、无注册、无 API Key 硬编码；用户配置的 Key 走 UncloseVault AES-256）
2. **无构建**（`demo.html` + `site.webmanifest` + `sw.js` 三文件可直接托管，`package.json` 仅声明 playwright 测试依赖）
3. **单文件可部署**（GitHub Pages/Vercel/Netlify/Nginx/CDN 任意静态托管）

**任何 v4.2+ 改动不得破坏此三角**。若某项升级必须引入构建（如 v6 模块化），须用 `vite-plugin-singlefile` 等方案保持"部署产物仍是单文件"。

### P0-1（v4.2）引入引擎1.5：本地 WASM TTS（Kokoro），摆脱外部端点 + 系统音色双重依赖

**根因**：v4.1 的降级链在"在线端点宕机"且"系统无中文语音包"时直接塌方到文本兜底（无声）。这是最严重的体验断裂（L1 失效）。

**方案**：在引擎1（在线）和引擎2（浏览器 SpeechSynthesis）之间插入引擎1.5 —— 基于 WASM 的本地高质量 TTS，不依赖外部服务，不依赖系统语音包。

**候选技术（v4.1 联网调研已确认，全部待真机测）**：

| 候选 | 模型 | 大小 | 质量 | 中文 | 许可 | 落地难度 | v4.1 调研结论 |
|------|------|------|------|------|------|---------|-------------|
| **Kokoro**（首选）| 82M 参数、34 声道、24kHz | q8f16 ONNX **86MB** | 高（待实测）| ✅ onnx-community 仓含 `zf_xiaobei/zf_xiaoxiao` 等 8 个中文 voice | Apache-2.0 | 低-中 | `kokoro-js@1.2.1` 浏览器原生（device:'wasm'），首选 |
| piper | VITS | ~40-200MB/语音 | 高（待实测）| ✅ 多说话人 | MIT | 低 | **❌ 弃用**：rhasspy/piper 已归档（2025-10-06），继任 piper1-gpl GPL-3.0，无 WASM 构建 |
| sherpa-onnx | VITS/Matcha | ~30-150MB | 高 | ✅ | Apache-2.0 | 中 | ⚠️ 落地难：无浏览器专用 npm 包，WASM 中文官方未 demo，需 Emscripten 自编译 |
| SpeechT5 | — | ~150MB | 中-高 | ❌ 仅英文 | MIT | 中 | **❌ 弃用**：基模型仅英文，无中文 ONNX |
| transformers.js + speech-t5 | — | ~150MB | 中-高 | ❌ | MIT | 中 | 作为英文退路 |

> **v4.1 调研背书**：官方 `uncloseai-speech` 自托管仓库已内置 Piper TTS + Kokoro TTS（8200 万参数、34 声道、24kHz、Apache-2.0）。Kokoro 82M 参数比 piper 更轻量，是更优 WASM 候选。

**落地技术点**：
1. 动态 `import('https://esm.sh/kokoro-js@1.2.1')`，按需加载模型（首次使用时从 HuggingFace `onnx-community/Kokoro-82M-v1.0-ONNX` 下载 `model_q8f16.onnx` 86MB，IndexedDB 缓存，Origin Private File System 兜底）。
2. 模型选择器：默认 `zf_xiaobei`（中文女声），可切换 `zf_xiaoxiao` 等。**落地时真机测确认出声 + 读音可懂，禁止宣称已验证**。
3. 降级链调整：`引擎1（在线）→ 引擎1.5（WASM Kokoro）→ 引擎2（浏览器）→ 引擎3（文本）`。cfg.engines_enabled 增加 `engine15` 开关。
4. WASM TTS 可产出 PCM/WAV blob，**离线模式也能下载**（修复 v4.1 离线不可下载缺陷）。
5. 徽章四态：`● 在线高质量 / ● 本地高质量 / ● 浏览器机械 / ● 离线文本`。
6. **WebAssembly SIMD 检测**：`WebAssembly.validate(SIMD模块)` 不支持时退非 SIMD 版本。
7. **WebGPU 加速探测**：`navigator.gpu` 存在时优先 WebGPU 推理（10x 性能，v6 才完整化，v4.2 仅探测）。
8. **Streaming TTS**：若 Kokoro 支持流式输出，用 ReadableStream 边合成边播放，首字节延迟降 60%+。
9. **SharedArrayBuffer + Worker**：把 WASM 推理放到 Web Worker，主线程不阻塞，COOP/COEP 头需配合（GitHub Pages 不支持，Vercel/Netlify/Cloudflare Pages 支持）。
10. **模型压缩**：ONNX quantization（int8，q8f16 已是）+ streaming 加载（fetch + ReadableStream + 渐进解析）。

**验收标准**：
- 断网 + 无系统中文包环境下，输入中文文本能产出可听的高质量语音（非机械音）。
- WASM 模型首次下载后缓存，二次使用零网络。
- E2E T_WASM_1/T_WASM_2/T_WASM_3 通过。
- WASM 模型加载不阻塞主线程（主线程帧率 ≥ 50fps）。

**风险**：
- 模型体积 86MB，首屏需按需加载（不阻塞主流程）。
- WASM 在 iOS Safari 的内存限制（**待真机验证，禁止预设数字**）。
- `zf_xiaobei` 中文 voice 能否实际加载出声 + 读音可懂**需真机浏览器测**，当前未做。这是 P0-1 暂缓的真正阻塞。
- COOP/COEP 头若静态托管不支持，SharedArrayBuffer 不可用，需退主线程 WASM。

**退避策略**：Kokoro `zf_` voice 真机测失败 → 试 `zf_xiaoxiao` → 试 sherpa-onnx WASM（需自编译）→ 三者均不可用则 P0-1 继续暂缓，先做不依赖 WASM 的节点（P1-2/P1-4/P2-*/P3-*/P4-*）。

**依赖**：`kokoro-js@1.2.1`（esm.sh CDN）+ `onnx-community/Kokoro-82M-v1.0-ONNX` q8f16 模型（HF CDN）。

### P1-2（v4.2）朗读字级高亮：karaoke 式跟随

**根因**：v4.1 朗读时无视觉反馈，用户不知道读到哪了。长文本体验差（L2 失效）。

**方案**：
- 在线引擎1：分块播放时，对应文本块高亮（已知 chunk 边界，`splitIntoChunks` 已返回 chunks 数组）。
- 浏览器引擎2：`SpeechSynthesisUtterance.onboundary` 事件提供 charIndex，可做字级高亮。
- WASM 引擎1.5：若支持时间戳对齐则字级，否则块级。

**落地技术点**：
1. 输入框下方加只读镜像层 `<div id="tts-mirror">`，高亮用 `<mark class="hl-current">` 包裹当前块/字。
2. 自动滚动当前块到可视区（`scrollIntoView({behavior:'smooth', block:'center'})`）。
3. 高亮颜色用 `--accent` 半透明（`rgba(99, 102, 241, 0.3)`）。
4. 停止时清除所有高亮（`stopPlayback` 已有 isStopped 守卫，复用）。
5. **整页朗读高亮**：`extractReadableText` 返回的 parts 数组与播放 chunks 对应，整页模式也能高亮（在原文位置插入 mark）。
6. **性能优化**：高亮用 `requestAnimationFrame` 批量更新，避免 boundary 事件高频触发导致掉帧。
7. **a11y**：高亮元素加 `aria-live="assertive"` 让屏幕阅读器同步朗读当前位置。

**验收标准**：
- 朗读时当前块高亮 + 自动滚动（T_HL_1）。
- 停止后高亮清除（T_HL_2）。
- 浏览器引擎下字级高亮（如支持 boundary 事件）（T_HL_3）。

**风险**：`onboundary` 在部分浏览器不触发或 charIndex 不准。需块级兜底（T_HL_1 始终保证）。

### P1-4（v4.2）分块策略增强：SSML 感知 + 语义边界

**根因**：v4.1 的 `splitIntoChunks` 按句末标点切分，但遇到 SSML 标签（v5 引入）会切断标签导致解析失败；遇到长无标点串硬切可能切断英文单词。

**方案**：
1. **SSML 标签保护**：切分时识别 `<break>`、`<prosody>`、`<emphasis>` 等标签，不在标签内部切分（v5 SSML 落地后启用）。
2. **语义边界优先**：优先在句号/问号/感叹号/分号处切分；其次在逗号处；最后硬切。
3. **CJK 与英文混合**：中文按字数，英文按单词（空格），不切断英文单词。
4. **段落感知**：`\n\n` 双换行视为强分割点，优先在此切分。
5. **CHUNK_SIZE 动态调整**：根据端点最大输入长度（从端点探测响应读 `max_input_length`）动态调整，避免超长被拒。

**验收标准**：U_SPLIT_1/2/3/4 全过。

**风险**：切分逻辑复杂化可能引入 bug。需充分夹具回归（扩展 `test-cases/` 加分块样本）。

### P3-1（v4.2）CSP nonce/hash 强化：移除 unsafe-inline

**方案**：

## 三、v5 迭代路线图（智能 + 可观测 + 平台化雏形）

### P5-1（v5）SSML 韵律控制

## 四、v6+ 迭代路线图（生态 + 平台化 + AI 原生）

**v6+ 主题词：从工具到平台，从平台到 AI 原生。**

### v6 候选方向

| 方向 | 描述 | 价值 | 难度 | 风险 |
|------|------|------|------|------|
| **朗读书签云端同步** | IndexedDB + 远端同步（用户自建后端）| 多设备续读 | 中 | 后端依赖 |
| **语音订阅源** | RSS/文章 URL → 自动朗读（podcast 生成）| 内容消费方式变革 | 中 | 内容合规 |

| **实时翻译朗读** | 输入中文 → 翻译 → 英文朗读（接翻译端点）| 跨语言无障碍 | 中 | 翻译质量 |
| **多人协作朗读** | WebSocket 多端同步播放（远程共读）| 教育/远程场景 | 高 | 实时性 |
| **朗读 API 开放** | 暴露 `window.chatTTS.speak(text, opts)` 供其他页面嵌入 | 平台化 | 低 | CSP/安全 |
| **WebGPU 加速** | WASM → WebGPU 推理（Kokoro/sherpa 支持）| 性能 10x | 高 | 兼容性 |

| **AI 摘要朗读** | 长文本 → LLM 摘要 → 朗读摘要 | 信息消费提效 | 中 | 付费 API |
| **多模态输入** | 图片 OCR → 文字 → 朗读；PDF 解析 → 朗读 | 无障碍场景拓宽 | 中 | 依赖大 |
| **情感朗读** | 文本情感分析 → 调整语速/音高/停顿 | 体验拟人化 | 高 | 模型依赖 |
| **朗读内容审核** | 敏感内容过滤（用户自定义关键词）| 合规 | 低 | 误判 |
| **协作标注** | 多用户为文本片段标注发音/韵律 | 众包语音数据 | 高 | 协调成本 |
| **离线模型分发** | P2P 模型共享（WebRTC）| 带宽节省 | 高 | 隐私 |

### v6 推荐优先序

1. **朗读 API 开放**（低成本，高复用，让本工具可被嵌入其他页面）
2. **语音订阅源**（差异化能力，竞品少）
3. **实时翻译朗读**（无障碍价值高）
4. **AI 摘要朗读**（信息消费提效，付费 API 需用户自带 Key）
5. **多模态输入**（OCR/PDF，无障碍场景拓宽）
6. **AI 语音克隆**（体验杀手锏，但合规复杂）
7. **架构演进**（方案 A→C，单文件模块化）

### v6 架构演进（可选，不破坏单文件部署承诺）

单文件 1470 行已接近极限。v6 可评估：
- **方案 A**：保持单文件，但 JS 抽到 `app.js`（ES module，`<script type="module" src="app.js">`）。部署仍是两文件（demo.html + app.js）。轻量。
- **方案 B**：Vite + 模块化构建，输出单 HTML（`vite-plugin-singlefile`）。开发体验好，部署产物仍是单文件。
- **方案 C**：Web Components（`<tts-player>`、`<chat-panel>`、`<read-page>`），零依赖组件化。

**推荐**：方案 A → 方案 C 渐进，永不破坏"单文件部署"承诺。方案 B 作为开发期工具，构建产物仍是单文件。
