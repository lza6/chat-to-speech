## 1. 第一性原理：这个工具的本质是什么

剥到最底层：**把"任意文字"变成"可听的声音"，在浏览器里、零成本、零依赖、即开即用**。

三条闭环是手段，本质需求是：
- **输入端**：文字从哪来（用户手输 / 聊天回复 / 整页正文 / 粘贴板 / 文件）
- **合成端**：文字怎么变声音（远端 TTS API / 浏览器内置 SpeechSynthesis / 二者降级链）
- **输出端**：声音怎么用（实时播放 / 下载 mp3 / 进度反馈 / 暂停续播）

v2 把"合成端"**单一押注在 `speech.ai.unturf.com`** 上，这是最大的架构脆弱点。v3 的核心升级方向：**合成端做双引擎降级链**，让工具在远端宕机时仍有声可出。

---

## 2. v3 升级总目标（一句话）

**把"单点依赖的 TTS 工具"升级为"多引擎自愈的朗读平台"**，同时把 v2 已有的 12 个功能打磨到"每个按钮点了都有真实反馈、每个状态都有可见反馈、长时间运行不泄漏不卡死"。

## 3. 改进项清单（按优先级 P0→P3 排序）

### P0-1：TTS 多引擎降级链（**v3 核心架构升级**）

**根因**：v2 闭环②③硬编码直连 `speech.ai.unturf.com`，端点一宕机（实测已持续 502）整链路死。

**方案**：建立三级降级链（不重写，在 `fetchTTSChunk` 外层包一层调度器）：

```
用户点朗读
   ↓
引擎1：speech.ai.unturf.com/v1/audio/speech（F5-TTS，42语音，质量最高）
   ↓ 失败（502/超时/网络错误）→ 自动降级
引擎2：浏览器原生 SpeechSynthesis API（零依赖，离线可用，但音色机械）
   ↓ 若浏览器无 SpeechSynthesis 或中文语音包 → 降级
引擎3：友好提示 + 一键复制文本（兜底，至少不黑屏）
```

**具体改动点（demo.html）**：
- 新增 `synthChain(text, voice, speed)` 调度函数：先试引擎1（复用现有 `fetchTTSChunk`），catch 后试引擎2，再 catch 试引擎3
- 引擎2实现：`window.speechSynthesis.speak(new SpeechSynthesisUtterance(text))`，映射 `voice` 名→浏览器中文语音（用 `speechSynthesis.getVoices()` 找 `zh-*`），支持 `rate` 参数对应 `speed`
- 状态栏明确显示当前用哪个引擎：`"🎤 在线 F5-TTS 合成中…"` / `"🔊 离线语音朗读（浏览器内置）"` / `"⚠️ 语音服务暂不可用，已复制文本"`
- 进度条在引擎2模式下隐藏（SpeechSynthesis 无法精确分块进度），改为"正在朗读"脉冲动画

**⚠️ 引擎2 实现注意事项（基于 Web Speech API 已知行为，部分待实测）**：
- `speechSynthesis.getVoices()` 在页面加载时**可能返回空数组**， voices 是异步加载的，需监听 `voiceschanged` 事件后才能拿到完整列表。引擎2 实现必须处理这个异步性，否则首次调用会因无语音而静默失败。
- `rate` 参数：Web Speech API `rate` 范围 0.1-10（1.0 默认），v2 的 `speed` 范围 0.5-2.0。**直接 `rate = speed` 数值上可接受但语义略有偏差**（speed=2.0 对应 rate=2.0 在 Web Speech 里是 2 倍速，合理）。落地时实测确认，必要时加缩放函数。
- 中文语音可用性因平台而异（Windows 有 Huihui/Yaoyao，macOS 有 Tingting，Linux 常缺失）。**必须在引擎2 启动前检查 `getVoices().filter(v=>v.lang.startsWith('zh')).length > 0`，无则直接跳引擎3**，不要假设有中文语音。
- `speechSynthesis.speak()` 在 iOS Safari 必须**在用户手势同步调用栈内**触发，不能在 await 之后。v2 的 `unlockAudio()` 已处理手势解锁，引擎2 调用需复用同一解锁时机。

**验收标准**：
- [ ] 拔网后点朗读 → 2 秒内切到浏览器内置语音出声，不卡死
- [ ] 端点恢复后下次朗读自动切回引擎1（不做"一旦降级永久降级"）
- [ ] 状态栏文案明确告知用户当前用哪个引擎（透明，不假装"成功"）
- [ ] 引擎2 在无中文语音的平台直接跳引擎3，不静默失败

**衍生价值**：这一升级让工具**永远不会哑火**——即使用户在飞机上、断网、端点维护，依然能朗读。这是"小白可用"的底线。

### P0-2：TTS 端点健康探测 + 语音列表本地缓存

**根因**：`initVoices()` 每次 reload 都 fetch `/v1/voices`，端点宕机时下拉只剩 3 个兜底，且无重试。

**方案**（不重写，增强 `initVoices`）：
- 首次成功拉取 42 语音后，**写入 localStorage**（key: `tts_voices_cache_v3`，带 24h TTL）
- 后续加载先读缓存即时填充下拉，再后台静默 refresh；refresh 失败保留缓存
- 端点探测：页面加载时发一个 HEAD 请求测 `/v1/voices`，结果存 `tts_endpoint_health`（`up`/`down`/`unknown`），用于决定 `synthChain` 起点引擎
- 下拉顶部加分隔项 `── 在线语音（42）──` / `── 离线语音（浏览器）──`，让用户知道来源

**改动点**：扩展 `initVoices()`，新增 `probeEndpointHealth()`，`VOICE_KEY` 旁加 `VOICES_CACHE_KEY`。

**验收标准**：
- [ ] 首次加载后断网刷新，下拉仍有 42 语音（来自缓存）
- [ ] 端点 down 时状态栏提示"在线语音暂不可用，已切换离线引擎"
- [ ] 健康状态有可视化（下拉旁小绿/红圆点）

### P0-3：聊天模型回复清洗（去 "thinking process" 前缀）

**根因**：实测当前 Hermes 模型 `Lorbus/Qwen3.6-27B-int4-AutoRound` 是**推理模型**，回复整段都是 `"Here's a thinking process:\n\n1. **Analyze User Input:**..."` 形式的思考过程，**不是答案前缀而是通篇推理**。v2 把整段喂给 TTS 会朗读出"一、分析用户输入"这种噪声。

**⚠️ 实测证伪的方案（不要用）**：我曾测试"用 system prompt 抑制思考"——
```
system: "你是中文助手，直接用简短中文回答，不要思考过程。"
```
响应**仍然**返回 `"Here's a thinking process:..."`。**system prompt 抑制对该推理模型无效**，不要把它当成解决方案。

**方案（分层，均标注验证状态）**：

1. **调查推理开关参数（待验证，优先）**：Qwen3 系列在 vLLM 部署下通常支持 `chat_template_kwargs.enable_thinking: false` 或 `extra_body: {enable_thinking: false}` 关闭思考模式。需在 `/v1/chat/completions` 请求体加该参数实测是否生效。**此方案未在本会话验证**（需向请求体加参数重测），落地 AI 应先做此实测再决定。
   - 验证命令示例：`curl -X POST .../v1/chat/completions -d '{"model":"...","messages":[...],"extra_body":{"enable_thinking":false}}'`
   - 若生效 → 库内部请求无法干预（库是黑盒），但闭环①的回复会变干净
   - 若不生效 → 走方案 2

2. **前端正则过滤思考块（兜底，已可落地）**：在 `extractReadableText()` 末尾加 `cleanAssistantText(text)`：
   - 剥离 `^(Here's a thinking process|思考过程|分析用户输入)[:：]?\s*` 开头直到首个换行空行的整块（推理模型通常思考与答案之间有空行分隔）
   - 若**整段都是思考无答案**（实测情况），则该条回复不送 TTS，状态栏提示"该回复为推理过程，已跳过朗读"
   - 不要只剥前缀留后文——后文可能仍是推理步骤

3. **库内 🔊 按钮无法干预**：库自带的 per-message 朗读按钮走库内部 `speakText`，前端无法拦截其文本清洗。此为已知限制，文档披露即可。

**改动点**：`window.UNCLOSEAI_SYSTEM_PROMPT` 可保留强化措辞（无副作用）；`extractReadableText()` 加 `cleanAssistantText` 过滤；状态栏加"已跳过推理过程"提示。

**验收标准**：
- [ ] 方案 1 实测后，若 `enable_thinking:false` 生效 → 回复不再含思考过程
- [ ] 方案 2 兜底：整页朗读时遇到纯推理回复自动跳过，不读出"分析用户输入"
- [ ] 不假装"system prompt 已解决"（实测证伪）

### P1-3：长文本分块策略升级（按句切分，不按字数硬切）

**根因**：v2 `splitIntoChunks` 按 500 字硬切，可能把"你好。"切成"你好" + "。"，TTS 在断句处停顿异常，听感割裂。

**方案**（改 `splitIntoChunks`）：
- 优先按句号/问号/感叹号/换行切分，每块不超过 500 字
- 中文标点 `。！？；` + 英文 `.!?;` + 换行作为分隔符，分隔符保留在块尾
- 段落级切分优于句子级（一段一块，段长超 500 再按句切）

**改动点**：重写 `splitIntoChunks`（约 15 行）。

**验收标准**：
- [ ] 朗读"你好。世界。"两块之间有自然停顿
- [ ] 不再出现"你好"和"。"被切到不同块导致的怪异停顿

### P1-4：播放队列竞态加固

**根因**：v2 用 `speakRequestId` 防竞态，但快速连点 + 自动播放被拦 + 降级链切换三者叠加时仍可能残留 `currentAudio`。

**方案**：
- `stopPlayback()` 末尾加 `currentPlaybackResolve = null` 的双重置空（已有，确认）
- 新增 `playbackState` 枚举（`idle`/`synthesizing`/`playing`/`paused`/`blocked`），所有 handler 检查状态而非散落的布尔
- 降级链切换时强制走 `stopPlayback()` 再起一轮，避免两引擎同时抢 `currentAudio`

**改动点**：把 `isSynthesizing`/`isStopped`/`audioUnlocked` 三个布尔收敛为 `playbackState` 状态机（约 30 行重构，不算大改）。

**验收标准**：
- [ ] 快速连点 10 次朗读按钮，不卡死不串音
- [ ] 播放中切降级引擎，旧音频立即停

### P1-5：下载功能强化（格式选项 + 文件名优化）

**根因**：v2 下载固定 mp3，但引擎2（SpeechSynthesis）无法产出 blob（浏览器内置不暴露音频流），下载按钮在离线模式下会失效却无提示。

**方案**：
- 下载按钮点击时检查 `audioBlobs.length`：有 → 正常下载；无 → 若当前是引擎2模式，提示"离线语音无法下载，请切换在线引擎后重试"
- 文件名加语音+语速+日期：`tts-aria-1.0x-20260906.mp3`
- 新增"复制文本"次级按钮（引擎3兜底场景的天然延伸）

**改动点**：`downloadBtn` handler 加守卫；文件名模板更新。

**验收标准**：
- [ ] 离线模式下点下载，状态栏明确提示不可用，不静默失败
- [ ] 在线下载文件名包含语速信息

## 7. 风险与边界（诚实披露）

1. **TTS 端点持续 502 可能是长期维护**：若 uncloseai-speech 项目停摆，引擎1 长期不可用，v3 实际只剩引擎2（浏览器内置）。此时工具仍有声可用，但音色机械。**这是 v3 降级链的核心价值所在**。
2. **浏览器 SpeechSynthesis 中文语音质量参差**：Windows Edge 自带 "Microsoft Huihui/Yaoyao" 质量尚可；Linux 多数发行版无中文语音包，引擎2 也会失败 → 走引擎3 文本兜底。**此条为常识推断，未在所有平台实测**，落地时需在目标平台用 `speechSynthesis.getVoices().filter(v=>v.lang.startsWith('zh'))` 实测确认。
3. **iOS Safari SpeechSynthesis 限制**：需用户手势触发，与 v2 的 autoplay 解锁机制兼容。**未真机实测**。
4. **Service Worker scope 限制**：Blob URL 注册 SW 在 Chrome 不可靠（v2 已论证），v3 用标准 scope 注册。
5. **库 `uncloseai.js` 仍为远程依赖**：若 uncloseai.com 域名失效，聊天闭环死。v3 不解决此依赖（属上游风险），但闭环②③不依赖库，仍可用。
6. **P0-3 方案 1（enable_thinking 参数）未实测**：本会话仅实测了 system prompt 抑制（失败），未测 vLLM 的 `enable_thinking:false` 参数。落地 AI 必须先实测再下结论。
7. **SpeechSynthesis `rate` 参数对应关系**：指南假设 `rate` 可映射 `speed`（0.5-2.0）。Web Speech API 的 `rate` 范围是 0.1-10（1 为默认），**不是 1:1 映射**，落地时需做 `rate = speed`（数值相近，1.0 对 1.0）并实测音速是否合理，可能需 `rate = 0.5 + speed * 0.5` 之类的缩放。

## 8. 不做什么（YAGNI 约束）

明确**不做**这些，避免过度工程：
- 不引入构建工具（Vite/Webpack）—— 单文件 HTML 是核心优势
- 不引入框架（React/Vue）—— 原生 JS 够用
- 不自建后端 —— "纯前端零成本"是产品定位
- 不做用户系统/云同步 —— 与"无需注册"冲突
- 不做语音克隆上传 —— 超出 uncloseai.js 能力，属上游职责
- 不做实时字幕/翻译叠加 —— 超出"聊天转语音"范畴
- 不重写 demo.html 结构 —— 严禁大幅重构（用户明确要求）

## 9. v3 完成后的"终极形态"愿景

一个 **10KB 级单文件 HTML**，浏览器打开即用：
- 输入任意文字 → 朗读（在线 42 语音 / 离线浏览器语音，自动降级）
- 聊天对话 → 回复可一键朗读（无噪声前缀）
- 整页内容 → 智能提取正文朗读
- 下载 mp3 / 复制文本 / 历史回听 / 主题三态 / 键盘全操作
- 断网不死、端点宕不哑、长跑不泄、连点不乱
- 真正的"小白打开就会用、高手键盘全搞定"

这个工具的价值不在"功能多"，而在"**永远可用**"——v3 的多引擎降级链就是为这个"永远"买的保险。
