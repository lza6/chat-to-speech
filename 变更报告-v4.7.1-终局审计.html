一、上下文：问题是在什么背景下被发现的

这个项目是一个纯前端、单文件的「聊天 + 朗读」工具（demo.html，3132 行）。它的承诺是：无注册、无 API Key、可静态托管、离线可用。VERSION 停在 4.7.0，此前已积累 116 项测试基线。

本次会话的任务不是「加功能」，而是终局审计——把项目当成明天就要交付给真实用户的产品，重新审视一遍。方法上做了两件关键的事：

  1. 派两个独立侦察代理并行扫描：一个逐节点核验规划文档里的功能是否真实落地；一个专找「看起来有、其实不能用」的假功能。
  2. 不采信代理的结论，亲自用浏览器复现。这一条至关重要——静态 grep 说「按钮坏了」，和浏览器里点一下真的没反应，是两种证据等级。
为什么必须亲自复现：审计代理报告说「#timeline-panel 不存在所以按钮是死的」。这是静态确认，不是已验证。项目自己的铁则写着「禁止静态确认冒充已验证」。所以我写了 e2e-test-p0-deadbtn.cjs，在真实 Chromium 里点击按钮、读 aria-expanded、量计算样式。结果显示 4 项失败——静态结论被真实运行坐实了。

二、直觉：为什么这些问题之前没被发现

四个 P0 有一个共同的、反直觉的特征：它们都是「静默失败」。

按钮点击没反应，不会抛异常、不会报错、不变灰、不弹提示——它只是什么都不发生。而之前的 116 项测试全都通过，因为测试测的是「功能存在时是否工作」，而这些问题出在「功能接线断了」。

P0接线断了，但代码看起来完全正常

wireTimelineUI() 函数写得毫无破绽：取按钮、取面板、绑事件、切换 aria-expanded、重新渲染。逻辑自洽，读起来是对的。

它唯一的问题是第一行就 return 了：

const panel = document.getElementById('timeline-panel');
if (!btn || !panel) return;   // ← panel 永远是 null，函数到此为止

根因是 v4.6 的一次重构：为了治理「面板太多太乱」，把时间线和记忆收进了 #data-panel 的页签结构。HTML 改了，但这个 wiring 函数还在找已经不存在的旧 ID。重构漏网了。

这解释了一个常见的困惑：为什么测试全绿但产品是坏的。因为测试的粒度和缺陷的粒度不匹配——测试验证的是纯函数和元素存在性，缺陷藏在「元素之间的连接」里。

function activateDataTab(name) {

    else if (name === 'timeline') renderTimeline();

}

P1：用户什么都没听到，界面却说「播放完毕」

这是语义正确性问题，比死按钮更值得警惕。在线合成路径长这样：

const r = await playBlob(blobCache[i]);
if (r === 'stopped') break;
if (r === 'error') { throw ... }          // 正确处理
if (r !== 'blocked') audioBlobs.push(...);
if (r === 'blocked') break;               // blocked 跳出循环
...
if (!isStopped && myId === speakRequestId) return 'ok';   // ← 却返回 'ok'！

'blocked' 是浏览器拦截自动播放时的返回值。此时用户一个字都没听到，但循环 break 之后代码径直返回 'ok'，speak() 随即显示「播放完毕。」并写入历史记录。

讽刺的是，状态机里早就定义了 blocked: 'stopped' 这条转移——但它从未被调用过。全文件只有四处 playState.apply()：speak / done / error / stopped，唯独漏了 blocked。

这与项目历史上修过的 P-13 是同一类缺陷。P-13 的记录写着「播放失败被静默当成功」，当时修了 error 路径，但 blocked 是漏网的同伙。这说明修一个案例时没有系统性地检查同类路径。

修法：抽出纯函数做单点映射，把「播放结果 → 链路返回值」的决策集中到一处，并让它可被单元测试直接覆盖：

function playResultToChainResult(r) {
    if (r === 'ended')   return { chain: 'ok',      playAction: 'done' };
    if (r === 'stopped') return { chain: 'stopped', playAction: 'stopped' };
    if (r === 'blocked') return { chain: 'blocked', playAction: 'blocked' };
    return { chain: 'error', playAction: 'error' };  // 'error' 及一切未预期值
}

注意最后一行的防御性设计：任何未预期的返回值都降级为 error，绝不静默成功。这是「失败必须显式」原则的落地。

4.3 审查线程还发现：状态机转移是空操作

我加的 playState.apply(m.playAction) 在在线路径上什么都没做。因为 playState 全程停在 preparing（全代码没有任何一处 apply('playing')），而 done / stopped / blocked 对 preparing 都是非法转移：

idle        speak   -> preparing
preparing   done    -> FALSE（正常结束：无操作）
preparing   stopped -> FALSE（用户停止：无操作）
preparing   blocked -> FALSE（被拦：本轮想设的状态没设上）
preparing   error   -> errored  ← 只有 error 生效

修法：在 await playBlob 之前补 playState.apply('playing')，让终结态转移合法。另外，我在 speak() 里写的注释"状态已是 stopped（playBlob 内已 apply）"与事实不符——playBlob 从不碰 playState。注释已更正。

九、一个更重要的发现：规划的 15 项功能，14 项从未实现
